# 아파트썸 실거래 랩 — 국토부 실거래가 분석 사이트

무료 (국토부 공공 API + Netlify 무료 티어).

## 환경변수

| Key | 용도 | 필수 |
|---|---|---|
| `DATA_GO_KR_KEY` | 국토부 실거래 API (data.go.kr, Decoding 키) — 매매(`/api/analyze`)·분양권전매(`/api/presale`)·전세(`/api/rent`) 공용 | 필수 |

접근코드 잠금은 제거됨 — 사이트가 공개 상태이므로 링크 유출 시 API 한도 소모 주의.

## 배포

**GitHub 저장소 + Netlify 연동을 권장** (아래 배치 수집 기능은 GitHub Actions가 리포에 데이터를 커밋하고,
그 커밋을 Netlify가 자동 배포하는 구조라 GitHub 연동이 전제됨). 기존에 Deploys 탭 드롭 방식만 쓰고 있었다면
Site settings → Build & deploy → Link repository 로 이 폴더를 올린 GitHub 저장소를 연결.

## 배치 데이터 수집 (GitHub Actions) — 속도 개선용

기존 구조는 사용자가 검색할 때마다 국토부 API를 실시간 호출(+CDN/브라우저 캐시)하는 방식이라 첫 조회가 느릴 수 있음.
이를 보완하기 위해 GitHub Actions가 **서울·경기·인천 73개 지역**의 매매·분양권·전세·세대수 데이터를 미리 수집해
`data/` 폴더에 JSON으로 커밋해두고, Netlify 함수는 이 정적 파일이 있으면 국토부 API 호출 자체를 생략하고 즉시 응답한다.
(정적 파일이 없거나 읽기 실패 시엔 기존과 동일하게 라이브 조회로 자동 폴백 — 동작 자체엔 영향 없음)

### 준비
1. GitHub 저장소 → Settings → Secrets and variables → Actions → New repository secret
   → `DATA_GO_KR_KEY` 에 국토부 API 키(Decoding) 등록 (netlify 환경변수와 같은 값)
2. 저장소 Settings → Actions → General → Workflow permissions → **Read and write permissions** 체크
   (Actions가 `data/` 커밋을 푸시하려면 필요)

### 최초 백필 (5년치 한 번에 채우기)
Actions 탭 → "실거래 데이터 배치 수집" → Run workflow → `months=60`, `force=true` 로 1회 수동 실행.
지역 73개 × 60개월 × 3종(매매/분양권/전세) 조회라 시간이 꽤 걸릴 수 있음(수십분 단위).
세대수는 "세대수 데이터 배치 수집" 워크플로를 별도로 수동 실행(Run workflow).

### 이후 자동 스케줄
- **매매/분양권/전세**: 격월(2개월 간격) 1일 새벽(KST 03:30) 자동 실행(2026.07 매월→격월로 완화) — 하이브리드 모드에서 최근 2개월은 Netlify 함수가 매 요청마다 실시간 조회로 항상 커버하므로, 배치는 그 이후(2개월 이전) 과거월만 채우면 됨. `--refresh=4`(최근 4개월 재조회) 창이 배치 간격(2개월)보다 넉넉해서, 한 번 실행이 실패해도 다음 배치가 무리 없이 따라잡을 여유가 있음. 그 이전 과거월은 이미 있으면 스킵
- **세대수**: 격월(2개월 간격) 자동 실행(2026.07 매월→격월로 완화) — 값이 거의 안 바뀌므로 이 정도 주기면 충분
- 두 워크플로 모두 `.github/workflows/`에 있고, 데이터가 바뀌면 자동 커밋 → Netlify가 그 커밋을 감지해 자동 재배포

### 참고
- `scripts/collect-trades.mjs`, `scripts/collect-hhcnt.mjs`: 수집 스크립트 (로컬에서도 `DATA_GO_KR_KEY=xxx node scripts/collect-trades.mjs --only=11680` 처럼 부분 실행 가능)
- `shared/regions.mjs`: 지역 코드·행정구역 개편 설정 원본(수집 스크립트가 참조). `index.html`의 `REGIONS`는 별개로 유지되므로, 지역이 추가/변경되면 두 곳 다 수동 동기화 필요
- 데이터 용량이 커지면(수년치 누적) 저장소 용량에 유의 — 필요 시 지역 범위를 좁히거나(`--only=`) 오래된 데이터를 별도 정리하는 것도 가능

## 기능
- **마지막 검색 지역 기억**: 단지 분석·단지 비교·지역/거래량/등락 랭킹 어디서 검색하든 그 지역을 localStorage(`apc:lastRegion`)에 저장, 다음 방문 시 지역 select 기본값으로 자동 적용(처음 방문 기본값은 강남구). 단지 비교는 여러 단지 각각 별도 지역 선택이 가능하지만, 저장은 메인 지역 select(새 비교 행 추가 시 기본값으로 쓰이는) 기준. 저장된 코드가 행정구역 개편 등으로 더 이상 유효하지 않으면 안전하게 강남구로 폴백

### 단지 분석 (최근 1~5년 선택, 기본 2년 — 2026.07 1년→2년 변경)
- **헤더 좌측 정렬**(2026.08): 단지명(h2)·메타 정보(동/준공년도/세대수/지하철 등) 줄이 기존엔 중앙 정렬이었는데, 즐겨찾기·공유 버튼이 우측 상단에 고정되어 있어 단지명이 길면 버튼과 부딪히기 쉬웠음 — 이 탭(`renderComplex`)에만 인라인 스타일로 좌측 정렬 적용, 다른 탭들의 `card-hd h2/.meta`(공용 CSS, 기본 중앙 정렬)는 영향 없음.
- **전용면적→평형 환산**: 국토부 API는 전용면적만 제공하고 공급면적(시장 통용 평형 표기 기준)은 안 주므로, 실거래 시장 통용 대응점(앵커) 10개로 구간 선형보간(`areaToPy()`, analyze.mjs/presale.mjs). 2026.07 호갱노노 실측 대조로 앵커 재보정(구 앵커가 신축 단지 상승한 전용률을 못 따라가 전반적으로 1~2평 낮게 표시됨): 39→18평, 49→21평, 59→25평, 74→30평, 84→33평, 99→38평, 110→42평, 130→49평, 150→58평, 165→65평. **알려진 한계**: 전용 84㎡ 같은 특정 면적은 실제로도 단지마다 32평/33평 등으로 표기가 갈려서(공급면적 자체가 단지·타입별로 다름), 앵커 방식으로는 어느 한 값을 골라도 다른 단지와는 어긋날 수 있음 — 이는 데이터 자체의 한계이지 계산 오류가 아님
- **이상치 자동 제외**: 직거래, 시세(동일 평형 전후 3개월 중앙값) 대비 30% 이상 낮은 거래는 평균·차트·추세에서 제외. 거래 내역에는 흐림 + "직거래/저가 제외" 태그로 표시
- **세대수 표시**(2026.07 추가, 같은 달 전체 탭으로 확대): 단지명 상단 메타 정보에 세대수 노출. 실거래가 API와는 완전히 별개인 국토부 공동주택 단지목록·기본정보 API(`AptListService2/getSigunguAptList` → `AptBasisInfoServiceV3/getAphusBassInfoV3`, `/api/hhcnt`)로 조회 — 시군구코드로 그 구에 등록된 단지 목록(kaptCode)을 받아 단지명을 매칭한 뒤, 매칭된 kaptCode로 세대수(`kaptdaCnt`)를 가져옴. 단지명 매칭은 공백 제거 후 완전일치→부분포함 순으로 비교(단지 분석의 `matchComplex`와 동일 방식)해 띄어쓰기 차이는 자동으로 무시됨. K-apt(공동주택관리정보시스템) 가입 단지만 나오므로 의무관리대상 미달 소규모 단지 등은 못 찾을 수 있고, 매칭 실패 시 조용히 세대수만 비워서 표시(단지 분석 자체엔 영향 없음). **캐시**: 세대수는 재건축 전까지 거의 안 바뀌는 값이라 서버(CDN) 90일 + 브라우저 `localStorage`(`apcHH:1`) 180일로 이중 캐시 — 재방문 시 API 호출 없이 즉시 표시됨. 다만 "못 찾음" 결과는 일시적 API 오류일 수 있어 클라이언트는 1일만 캐시하고 다음날 자동 재시도(찾은 결과와 TTL을 다르게 둠, 월별 실거래 캐시의 EMPTY_RETRY_TTL과 동일한 이유) — **CDN 쪽도 동일하게 못 찾음은 1일만 캐시하도록 수정(2026.07)**: 원래 found 여부와 무관하게 CDN을 90일로 고정해 둬서, 클라이언트가 1일 뒤 재시도해도 CDN이 계속 오래된 found:false를 돌려줘 재시도가 사실상 무의미했던 버그가 있었음(analyze.mjs·presale.mjs는 애초에 빈 결과·정상 결과의 CDN 캐시 기간을 다르게 뒀는데 hhcnt.mjs만 놓쳤던 부분). 처음엔 단지 분석·등락 랭킹의 "단기 저평가 단지"(비교 대상 목록)에만 붙어 있었는데, 이후 **단지 분석 이외의 모든 목록형 탭**(단지 비교 요약, 지역 랭킹의 기간 최고가 거래, 거래량 랭킹, 등락 랭킹의 상승률·하락률 상위, 분기·연간 저평가의 비교 대상 목록)에도 동일하게 세대수를 붙이도록 확대 — 한 화면에 같은 단지가 여러 목록에 걸쳐 나올 수 있어 (지역코드, 단지명) 기준으로 화면 렌더링 시점에 한 번만 조회해 공유(중복 API 호출 방지). **동시 요청 제한**(2026.07 추가): 지역 랭킹처럼 한 화면에 최대 100건씩(최고가 거래·거래량 각각) → 거의 200개에 가까운 단지의 세대수를 한꺼번에 조회해야 할 수 있어, 무제한 병렬 대신 최대 12건 동시 조회로 제한하는 간단한 큐를 둠(브라우저·Netlify 함수에 순간적으로 과도한 동시 요청이 몰리는 것 방지)
- **임대 단지 오매칭 수정**(2026.07, v108): 같은 이름을 쓰면서 일부 동만 임대인 단지(예: 봉천동 두산아파트 — 1·2단지 2,001세대는 일반분양/매매, 3단지 560세대는 임대)에서, 세대수 매칭이 임대 동 쪽(더 작은 세대수)으로 잘못 붙는 사례가 있었음. 매매 실거래(RTMS) 데이터에서 나온 단지명은 애초에 임대 세대일 수 없으므로(임대는 매매 자체가 불가), `matchKapt()`에서 후보 중 이름에 "임대"가 포함된 항목은 다른 비임대 후보가 있으면 제외하도록 수정 — 순수 임대 단지를 조회한 경우(비임대 후보가 아예 없는 경우)는 기존대로 그대로 매칭됨
- **세대수 캐시 무효화 누락 수정(HH_CACHE_VER 추가)**(2026.07, v119): v108에서 `matchKapt()` 로직 자체는 고쳤는데, 세대수는 브라우저 localStorage에 180일, `hhcnt.mjs`의 GET 엔드포인트는 Netlify CDN에 90일(durable)로 캐시돼 있어서 배포 후에도 예전(오매칭) 결과가 캐시에서 그대로 재사용되는 문제가 있었음(두산아파트가 v108 배포 후에도 계속 560세대로 보이던 원인) — 메인 실거래 데이터의 `CACHE_VER`와 동일한 패턴으로 `HH_CACHE_VER`를 신설해 localStorage 키(`apcHH:2`)와 GET 요청 쿼리(`&v=2`)에 반영, 매칭 로직이 바뀔 때마다 이 값을 올려 캐시를 강제로 무효화하도록 함
- **지하철 정보 추가**(2026.08, v159): `hhcnt.mjs`가 세대수와 함께 지하철 정보(`subwayLines`(호선 배열)·`subwayStation`·`subwayWalk`(도보시간, K-apt 원본 텍스트))도 함께 내려주도록 확장(`getAphusDtlInfoV4`). 단지 분석 헤더(`subwayMetaHTML`)에 세대수 옆으로 표시. 필드가 새로 추가된 것뿐이어도 옛 캐시엔 이 필드가 아예 없어서 `HH_CACHE_VER` 4→5로 올려 캐시 무효화(안 올리면 브라우저 180일·CDN 90일 캐시가 새 필드 없는 옛 응답을 계속 돌려줌).
- **지하철 검색(비공개 탭)**(2026.08): 지역+호선+도보시간(5/10/15분 이내)으로 단지를 찾는 탭 추가. 실거래(analyze.mjs) 기반이 아니라 `data/hhcnt/<지역>.json` 배치 데이터를 클라이언트에서 직접 fetch해 필터링 — 별도 서버 함수 없이 기존 정적 파일 재사용. 신저가·연간 저평가(동일 동) 탭과 동일하게 로고 5회 탭 제스처로만 노출(`SECRET_KEY` 공유). "5~10분이내"처럼 범위로 된 원본 텍스트는 최악값(상한) 기준으로 필터링(`parseSubwayWalk`) — "15~20분이내"인 단지가 "15분 이내" 필터에 잘못 걸리지 않도록. 지역 내 최근 3년 실거래를 조회해 "전용면적 평단가" 탭과 동일한 로직(`analyzePricePerPyeong`)으로 단지별 평단가를 계산해 **평단가 높은 순으로 정렬**(K-apt 단지명과 실거래 단지명 표기가 달라 `matchKapt()`와 동일한 정확일치→부분일치 방식으로 매칭) — 평단가 조회 실패 시 도보시간 순으로 폴백. 정렬 기준으로만 쓰고 화면엔 숫자를 노출하지 않음(수민 요청).

- 각 항목에 직전 최고가 대비 상승액·상승률(▲ 금액(%))을 함께 표시 — 단순히 "신고가"라고만 하지 않고 얼마나 올랐는지 바로 보이도록
- 정렬은 **가격 높은 순**(v113, 최초 구현은 갱신폭 큰 순)
- **평형 다중 선택**(v154, 2026.07 — 최초 구현은 지역/거래량/등락 랭킹과 동일한 단일 구간 선택이었음): 여러 평형 구간을 동시에 선택 가능(예: 23~27평+37~41평만, 그 사이는 제외). 연식 필터도 지원, 층수 필터는 없음
- **지역 복수 선택 지원**(v150, 2026.07 — 최초 구현은 단일 구 기준이었음): 저평가 3탭과 동일하게 최대 5개 지역까지 칩으로 담아 통합 조회 가능(`regionSelMax()`). 거래량·등락 랭킹은 여전히 단일 구 기준

### 신저가 (비공개 탭 — 신고가와 대칭 구조로 추가, 로고 5회 탭으로 노출)
- 조회기간은 신고가와 다르게 **1년(12개월) 고정**(`analyzeNewLow`, 2026.08 최초 2년→1년으로 축소, 수민 요청) — 표본(months)이 항상 1년 창이므로 "1년 내"라는 표현이 정확히 그 창을 가리킴
- **로직 전면 변경**(2026.08, 수민 요청): 기존엔 "직전 최저가보다 더 낮은 가격을 최근 한 달 내 새로 찍었는지"(동일가 재현 제외)로 판정했는데, 이제는 **"1년 내 최고가(peak) 대비 최근 한 달 이내 거래가 -10% 이상 빠졌는지"**로 기준을 바꿈. 예전 방식은 직전 최저가 대비 하락폭이 미미해도(예: -0.5%) 잡히던 반면, 새 방식은 실제 눈에 띄는 급락만 남도록 임계값(`DROP_THRESHOLD = 0.10`)을 둠
- 단지+평형별로 1년 표본 중 최고가(peak)를 구하고, 그중 최근 30일 이내 계약 & peak 대비 10% 이상 낮은 거래들을 후보로 추린 뒤 가장 하락폭이 큰(가격이 가장 낮은) 거래를 대표로 채택
- **1년 최고가 자체도 화면에 표시**(2026.08): 목록 각 행에 "1년 최고 X.X억" 라벨(취소선 없이 담백하게, 시도했다가 수민 요청으로 취소선 제거)을 가격 왼쪽에 놓고 그 오른쪽에 실제 하락 가격을 큼직하게 배치 — 흔한 "정가→할인가" 읽는 순서
- **-25% 이상 하락은 이상치로 제외**(2026.08, 수민 요청): 10% 이상 하락만 인정하던 하한에 더해, -25% 이상 빠진 거래는 오히려 제외하는 상한도 추가(`MAX_DROP` — 최초 0.30에서 0.25로 더 좁힘) — 시세보다 지나치게 낮은 거래는 특수관계 매매(가족간 저가 양도 등, `direct` 필드로 못 걸러지는 경우도 있음)나 급전 필요에 의한 이례적 급매일 가능성이 높아, "완만하지만 뚜렷한" 하락 신호(10~25%)만 신저가로 인정
- **탭 이름 "신저가"→"하락 거래"로 변경**(2026.08, 수민 요청): 탭 버튼·결과 카드 배지·섹션 제목·빈 결과 문구 등 화면 표시 라벨만 변경, 내부 함수/변수명(`analyzeNewLow`, `mode==='newlow'` 등)은 기존 컨벤션대로 그대로 유지
- 표본 3건 이상, 1~5층 제외(층수 할인 왜곡 방지), 직거래 제외 — 신고가와 동일한 원칙 유지
- 정렬은 **하락률(gapPct) 큰 순**(예전엔 가격 낮은 순) — "얼마나 빠졌는지"가 이 탭의 핵심이라 정렬 기준도 그에 맞춤
- `prevMax`/`gapAmt`/`gapPct` 필드명은 그대로 재사용하되 의미가 "직전 최저가 대비"에서 "1년 최고가 대비"로 바뀌었으므로, 화면 문구(메타 라인·안내 문구·출처 노트)도 함께 갱신

### 등락 랭킹 (최근 4개월 고정, 최근 2개월 vs 이전 2개월)
- 최근 2개월/이전 2개월 비교라 기간 선택(1~5년)이 필요 없음 — 분석 자체는 최근 4개월 데이터만 사용하지만, **API 조회는 단기·분기·연간 저평가와 함께 항상 24개월치로 통일**(2026.07 변경, 네 탭 공통 캐시 공유 목적 — 예전엔 4개월만 조회해 API 호출·로딩이 가장 가벼운 탭이었으나, 캐시 일관성을 우선해 다른 저평가 탭들과 맞춤)
- 평형 구간 필터: 전체 / 17~22 / 23~27 / 28~31 / 32~36 / 37~41 / 42~46 / 47~51평 (지역 랭킹과 동일)
- 단지별 최근 2개월 평균 vs 이전 2개월 평균 비교 — 상승률 상위 10 / 하락률 상위 10
- 각 구간 최소 2건 이상 거래 있어야 집계 (표본 부족 시 "데이터 없음" 표시)
- 단지명 클릭 → 12개월 상세 분석으로 바로 이동 (지역 랭킹과 동일한 동선)
- (2026.07, v122) 예전엔 이 화면 안에 "단기 저평가 단지" 섹션이 같이 있었는데, 별도 공개 탭(**단기 저평가**, 바로 아래 항목)으로 분리했음. 이 탭은 이제 상승률·하락률 상위만 표시

### 단기 저평가 (2026.07, v122 — 등락 랭킹에서 분리한 별도 공개 탭)
- 등락 랭킹과 마찬가지로 잠금 없이 누구나 바로 보임(반기/연간 저평가와 달리 비공개 탭 아님) — 예전에 등락 랭킹 화면 하나에 얹혀 있던 걸 독립 탭으로 분리한 것뿐, 계산 로직·API 조회(24개월 공용 캐시)는 그대로
- 단지마다 "이전 2개월 평균가가 나와 ±2% 이내인 단지 중 가격이 가장 가까운 최대 5개"를 비교군으로 구성(고정 구간이 아닌 상대 비율 기준이라 경계값 근처에서 억지로 갈리는 문제 없음). 비교군 후보는 **최근·이전 2개월 구간 각각 거래 2건 이상**인 단지만 인정(전체 단지 최소 기준과 동일 — 이상치인 직거래·저가 거래는 이미 markOutliers에서 걸러진 뒤라 3건으로 더 엄격하게 잡을 실익이 적다고 판단해 2026.07 완화). **매매 실거래만 집계**(분양권·입주권은 준공 전 시세·전매 이슈 등으로 왜곡 소지가 있어 제외). **20~37평만 집계**(초소형·초대형은 표본이 적고 가격 스케일이 달라 같은 비교군으로 묶기 부적절해 제외). "최근 2개월 평균가"가 비교군의 **표준 중앙값**(짝수 그룹은 가운데 두 값의 평균)보다 **5% 이상 낮아진 단지만** 표시, 준공년도·표본건수(n)·비교 대상 단지명 노출(클릭 이동 가능), 정렬은 격차(gapAmt, 금액 기준) 우선·동률 시 표본 많은 쪽 우선. 본인 포함 그룹원 3개 이상만 비교(이건 비교군 규모 최소치라 그대로 유지). **평형·연식 필터 UI 자체가 없음** — 항상 20~37평 고정 기준으로 계산됨(반기/연간 저평가와 동일한 패턴)
- **알려진 한계**(의도적으로 남겨둔 트레이드오프, 필요 시 후속 조치): 절대가 기준 비교라 평형이 다른 단지끼리 우연히 가격이 비슷하면 비교군으로 묶일 수 있음(평당가 기준 그룹핑을 시도했으나 사용자 요청으로 절대가로 원복) / 1~4층 제외 로직(2026.07 5층 이상으로 강화)이 저층 위주 단지 전체를 통계에서 제외시킬 수 있음 / 비교군 표본 부족(각 구간 3건 미만)은 필터링하지만, 3건 이상이어도 비교군 자체가 이상치일 가능성은 별도 검증 안 함 / ±2%·5% 임계값은 시장 변동성과 무관하게 고정값 / "저평가"라는 표현이 실측치(또래 대비 덜 오름)보다 강하게 들릴 수 있음 — 하자·노후화 등 정당한 사유로 뒤처졌을 가능성과 구분 안 됨
- **지역 복수 선택 지원**(v137, 2026.07): 단기·반기·연간 저평가 3개 탭 모두 지역 랭킹과 동일하게 여러 구를 칩으로 담아 통합 조회 가능. 그룹핑 키에 구(`gu`)를 포함해 서로 다른 구의 동일 단지명이 잘못 합쳐지지 않도록 처리, 결과 목록에도 구 이름 표시. **최대 5개 지역까지만 선택 가능**(v141, 2026.07) — 지역 랭킹(최대 45개)과 달리 단지별 세대수까지 조회하는 무거운 계산이라 상한을 낮게 잡음(`regionSelMax()`). 추가 시점뿐 아니라 지역 랭킹에서 5개 넘게 쌓아둔 채로 이 탭들로 전환해도 자동으로 앞의 5개만 남도록 처리, 지역 선택 패널 타이틀에도 "지역 선택 (최대 5개)"로 상한 표시
- **최대 30개까지만 표시**(2026.07 10→30으로 확대): 300세대 이상 조건을 만족하는 단지 중 격차(가격 차이) 큰 순으로 상위 30개까지만 보여줌 — 후보가 그보다 많아도 세대수 조회를 앞에서부터 배치로 진행하다 30개가 채워지면 즉시 멈춤(로딩 속도를 위한 조기 종료 방식)

### 반기 저평가 (2026.07 추가, v123부터 공개 탭 — v130에서 "분기 저평가"→"반기 저평가"로 개명 + 층수 제한 삭제)
- 단기 저평가 탭(2개월 평균 기준, 위 항목)은 **그대로 유지**. 이와 별개로, "최근 6개월 최고가 vs 이전 6개월 최고가" 기준의 실험적 버전을 별도 탭으로 분리해 검토 중
  - **최초엔 "분기 저평가"(3개월 vs 3개월)로 구현했다가, v130에서 "반기 저평가"(6개월 vs 6개월)로 이름과 로직을 함께 변경** — 탭 이름과 실제 비교 구간이 어긋나지 않도록 `buildPeakRows()`의 최근/이전 구간 분리 기준을 `months.slice(0,3)/(3,6)`에서 `(0,6)/(6,12)`로 교체
  - **층수 제한 삭제**(v130, 최초 구현은 5층 이상만 집계) — 연간 저평가와 동일하게 전 층 포함으로 통일. 분양권·입주권 포함(단, 층 정보가 없는 분양권 일부는 이번 변경으로 더 이상 층수 조건에 의해 자동 제외되지 않으므로 표본에 포함될 수 있음)
  - 20~37평 구간 제한은 그대로 적용(직거래·저가 이상치는 markOutliers로 별도 제외)
  - 비교군은 이전 6개월 최고가 ±2% 이내 최대 5개, 최근 6개월 최고가가 비교군 중앙값보다 5% 이상 낮으면 표시 — 로직 구조는 기존과 동일하되 평균→최고가·2개월→6개월만 교체
  - "또래 대비 덜 오른" 단지보다 "동일 시세대에서 신고가를 못 따라간" 단지를 잡는 데 초점. 다만 최고가는 단일 거래에 좌우되기 쉬워 평균보다 이상치 영향을 더 받을 수 있음 — 두 지표를 나란히 비교해보고 반응 좋은 쪽으로 정식 반영 여부 결정 예정
  - 분석 자체는 6+6(최근 6개월 vs 이전 6개월)개월치만 사용하지만, **API 조회는 등락 랭킹·단기·연간 저평가와 함께 항상 24개월치로 통일**(2026.07 변경 — 네 탭을 오가며 검토할 때마다 서로 다른 개월수를 새로 조회하지 않고 같은 24개월 캐시를 공유하도록)

### 연간 저평가 (2026.07 추가, v123부터 공개 탭 — 탭 이름 "연간 저평가")
- 반기 저평가(위 항목)와 완전히 동일한 로직(최고가 기준, ±2% 이내 최대 5개 비교군, 5% 이상 격차, 20~37평 제한, 층수 제한 없음 등)을 그대로 사용하되, 비교 구간만 "최근 6개월 vs 이전 6개월"에서 "최근 1년 vs 이전 1년"(작년 대비 올해)으로 교체
  - 분석 자체는 12+12(올해 1월~현재월 vs 작년 1~12월) 캘린더 연도 비교를 그대로 쓰지만, **API 조회는 등락 랭킹·단기·반기 저평가와 함께 항상 24개월치로 통일**(2026.07 변경 — 네 탭 공통 캐시 공유가 목적. 분석에 실제 쓰이는 개월수(윈도우)는 그대로라 결과·기간 표시는 달라지지 않음, 다만 12월이 아닌 달에는 필요 개월수(현재월+12)가 24보다 적어 API로 24개월치를 받아온 뒤 그중 필요한 만큼만 걸러 씀)
  - "단기 신고가 흐름"이 아니라 "1년 단위 신고가 흐름"을 못 따라간 단지를 잡는 버전. 기간이 길어진 만큼 표본이 늘어 이상치 영향은 줄지만, 최근 몇 개월의 급격한 변화는 더 늦게 반영됨
  - 화면에 "※실거래가 기준으로 최근 호가와 다를 수 있음" 안내 문구 표시(청록색)
- **잠금 해제됨(v123, 2026.07)**: 예전엔 로고를 1.5초 이내 5회 연속 클릭하면 뜨는 비밀번호 모달(`aptsum26`)로 잠겨 있었는데, 다른 랭킹 탭들과 동일하게 항상 노출되는 공개 탭으로 전환 — 잠금 관련 코드(`logoClick()`/`peakPwModal`/`apc:peakUnlocked` 등) 전부 제거
- URL 공유(`buildShareURL`/`initFromURL`)도 이제 다른 탭과 동일하게 정상 연결됨(예전엔 의도적으로 제외돼 있었음)

### 단지명 자동완성
- 단지명 1자 이상 입력 시 해당 지역 최근 1년 거래 단지 중 일치 목록 드롭다운 (동·거래건수 표시)
- 지역별 목록은 최근 1년(매매) + 최근 1년(분양권) 거래 기준, 최초 1회만 조회 후 브라우저에 24시간 캐시 — 타이핑마다 API 호출 안 함
- 매매 실거래가 없는 분양권 전용 단지도 "(분양권)" 표시로 함께 뜸, 표기(공백 등)가 다른 같은 단지는 자동으로 병합
- **개명 이력 있는 단지 별칭 매핑**(`APT_ALIASES`): 사업 진행 중 단지명이 바뀐 경우(예: 흑석자이 — 준공 직전 "흑석리버파크자이"에서 개명) 과거 거래가 옛 이름으로 국토부에 남아있어도 새 이름으로 검색하면 함께 찾아짐, 자동완성에도 하나로 병합 표시. 새로운 개명 사례 발견 시 이 매핑에 추가 필요(추정 금지 — 개명 이력 웹 검색으로 확인 후 추가). **개명이 아닌 경우도 대응**(2026.08): 인덕원삼성 — K-apt 등록명("인덕원삼성")과 국토부 실거래 등록명("인덕원마을삼성")이 애초부터 서로 달라서, 역세권 탭에서 클릭(`quick()`)해도 단지 분석에서 못 찾던 문제. 개명은 아니지만 "검색어 A로도 실거래 등록명 B를 찾게 한다"는 메커니즘 자체는 동일해 `APT_ALIASES`에 함께 등록해 해결.
- 단지 분석·단지 비교 입력창 모두 지원

## 속도·호출 구조 (v2 아키텍처)

- 서버는 월 데이터 전달만, 분석은 브라우저에서 수행
- 긴 기간은 12개월 단위 샤드로 병렬 조회 → 5년 검색도 1년 검색과 비슷한 체감 속도
- **매매·분양권 병렬 조회**(2026.07 수정): 예전에는 매매 조회가 끝난 뒤 분양권 조회를 순차로 기다려서 두 응답 시간이 그대로 합산됐음(특히 등락/지역/거래량 랭킹에서 체감 지연 컸음) → `Promise.all`로 동시 요청하도록 수정, 한쪽만 느려도 전체 대기시간은 더 느린 쪽 하나 기준
- **서버 함수 내 static/live 병렬화**(2026.07 추가): 최근 2개월은 static 캐시를 아예 안 보고 무조건 국토부 API로 실시간 조회하는데, 예전엔 과거월 static 파일 조회가 끝나야 이 실시간 조회를 시작해서 "static 조회 시간 + 국토부 API 왕복 시간"이 그대로 더해졌음(CDN 30분 캐시가 만료된 직후 첫 요청에서 특히 체감) → 최근 2개월 live 조회와 과거월 static 조회를 동시에 시작하도록 수정(`analyze.mjs`/`presale.mjs`/`rent.mjs` 동일 적용), static에서 못 찾은 과거월만 그 결과를 보고 추가로 한 번 더 live 조회
- 받아온 월 데이터는 브라우저에 캐시 (과거월 영구, 최신 4개월 6시간 — 2026.07 2개월→4개월 확대 + 30분→6시간 변경: 국토부 신고기한(최대 30일)으로 실거래가 계약월보다 늦게, 심지어 다다음달에 뒤늦게 등록되는 경우가 있어 2개월·30분으로는 놓치는 사례 발생. 특히 "저평가" 탭처럼 과거월 최고가를 계산에 고정적으로 쓰는 로직은 뒤늦게 반영된 신고가를 못 따라잡을 수 있어 확대. 신고 지연은 시간 단위가 아니라 일 단위라 30분은 과도하게 잦았던 것이라 6시간으로 완화) → 같은 지역에서 단지 바꿔 검색하면 API 호출 0회로 즉시 분석(단, 최신 4개월은 6시간마다 재확인이라 그 안에서는 호출 발생 가능)
- **캐시 자가복구**: 과거월이라도 캐시된 결과가 0건이면 30분 후 자동 재확인함 (API 일시 오류로 빈 캐시가 영구 박제되는 것 방지). 진짜 거래 없는 달은 다시 0건으로 채워질 뿐이라 안전함. **0건이 아니어도(거래는 있었지만 조회 시점엔 일부만 신고돼 있던 경우) 캐시가 7일 넘게 지나면 한 번 더 재확인**(2026.07 추가 — "저평가" 탭이 뒤늦게 추가·정정 신고된 거래를 계속 놓치던 문제 보완, 완전한 1회성은 아니고 재확인할 때마다 캐시 시각이 갱신되므로 이후 다시 7일 주기로 반복 확인됨)
- **고아 캐시 자동 청소**(2026.07): `CACHE_VER`를 올릴 때마다 이전 버전 localStorage 데이터가 자동으로 안 지워지고 계속 쌓이면, 여러 지역을 오래 테스트한 브라우저에서 용량 한도를 넘겨 캐시 저장 자체가 매번 실패(→ 매번 API 재조회로 계속 느려짐)하는 문제가 있었음. 페이지 로드 시 현재 `CACHE_VER`와 다른 `apc:`/`apcP:` 접두사 키를 전부 지우도록 수정 — **단, 최초 구현 시 "apc:favs"·"apc:pyBand"처럼 버전 태그가 없는 즐겨찾기·설정값까지 전부 같이 지워버리는 회귀 버그가 있었음(새로고침하면 즐겨찾기가 사라짐)**. "apc:숫자:" 형태(월별 캐시 전용)만 정규식으로 정확히 골라 지우도록 즉시 재수정
- 일 한도 100만 콜 기준 사실상 무제한
- **검색 경합(race condition) 방지**(2026.07, v104): 지역 랭킹에서 단지명을 클릭해 단지 분석으로 넘어갈 때처럼, 이전 검색(`search()`)이 API 응답을 기다리는 도중(await) 새 검색이 시작되면 먼저 시작된 검색이 나중에 끝나면서 최신 결과를 덮어써 엉뚱한 탭의 표가 뜨는 문제가 있었음. `search()` 호출마다 증가하는 토큰(`searchToken`)을 발급해, 렌더링·에러 표시·로딩 해제 직전에 자신이 여전히 최신 요청인지 확인 후 아니면 조용히 폐기하도록 수정
- **동일 경합 추가 케이스 수정**(2026.07, v105): `quick()`뿐 아니라 **탭 전환(`setMode()`)**과 **뒤로가기 복원(`restoreView()`)** 시점에도 검색 도중이었다면 같은 문제가 재현될 수 있었음(예: 로딩 중 탭을 바꾸거나 뒤로가기를 누르면, 늦게 도착한 이전 검색 결과가 방금 전환·복원한 화면을 도로 덮어씀) — 두 함수 시작 시에도 `searchToken`을 무효화하도록 확장
- **즐겨찾기 지역 클릭 시 신고가 탭 미반영 버그 수정**(2026.07, v111): `favRegionGo()`(즐겨찾기 지역 칩 클릭 시 바로 조회하는 함수)의 자동조회 대상 모드 목록에 신고가 탭이 빠져 있어서, 신고가 탭에서 즐겨찾기 지역을 눌러도 화면이 갱신되지 않던 문제 수정
- **평형 미분리로 인한 신고가 오탐 수정**(2026.07, v112): `analyzeNewHigh()`의 단지 그룹핑 키에 평형(py)이 빠져 있어서, 같은 단지의 서로 다른 평형(예: 84㎡와 149㎡)이 한 그룹으로 섞여 "최고가"가 계산되고 있었음 — 더 비싼 평형의 과거 거래 때문에 정작 방금 신고가를 찍은 다른 평형이 목록에서 누락되거나(또는 반대로 잘못 포함), 평형 필터를 걸었을 때와 안 걸었을 때 결과 개수가 안 맞는 원인이었음. 그룹핑 키에 py를 추가(`apt+umd+py+gu`)해 평형별로 독립적으로 최고가를 판정하도록 수정
